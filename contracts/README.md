# قرارداد داده و API

نسخهٔ فعلی `1.0.0-draft.1` است و برای هماهنگی سه عضو تیم آماده شده است؛ تصویب تیم هنوز
ادعا نمی‌شود. مدل‌ها در ماژول‌های `catalog`، `recommend` و `journey` تعریف شده‌اند. خروجی ماشین‌خوان
در `openapi.json` و نمونه‌های مستقل از دیتاست بزرگ در `examples/` قرار دارند.

## مسیرها

پیشوند: `/api/v1/catalog`

| روش و مسیر | خروجی | کاربرد |
| --- | --- | --- |
| `GET /offers` | `CatalogPage` | آفرهای مرتبط با محصول و فیلترها |
| `GET /offers/{offer_id}` | `{item: OfferCandidate, context}` | جزئیات یک آفر ثبت‌شده |
| `GET /products/{product_id}` | `{item: Product, context}` | جزئیات محصول و مشخصات فنی |
| `GET /shops` | `ShopPage` | دایرکتوری فروشگاه‌ها؛ شاهد فروش محصول نیست |
| `GET /meta` | `CatalogContext` | شناسه، نوع منبع، تعداد رکوردها و محدودیت‌ها |

`GET /health` خارج از این پیشوند است. `data_ready=false` یعنی هنوز دیتاست وارد نشده است.
API مسیر نوشتن یا بارگذاری فایل ندارد؛ import از CLI انجام می‌شود.

## Journey recommendations

`POST /api/v1/journey/recommendations` یک درخواست بدون وضعیت پایدار است و از Catalog
موجود و سرویس Recommendation استفاده می‌کند. بدنه از نوع `ShoppingRequest` است:

```json
{
  "request_id": "sample-request",
  "revision": 0,
  "criteria": {
    "q": "گوشی سامسونگ",
    "max_budget": "200000000",
    "price_unit": "IRR",
    "latitude": 35.7,
    "longitude": 51.4,
    "max_distance_km": 5.0
  },
  "comparison": null
}
```

بودجه با `max_budget` و واحد صریح `TOMAN` یا `IRR` ارسال می‌شود؛ مبلغ باید رشتهٔ اعشاری
دقیق یا عدد صحیح باشد. جایگزین آن `max_price_toman`، عدد صحیح به تومان، است؛ این دو روش
هم‌زمان مجاز نیستند. متن کالا، بودجه و مختصات لازم‌اند. محدودیت‌های متنی `city` و `area`
و `min_price_toman` در این مسیر پشتیبانی نمی‌شوند و به‌جای حذف‌شدن، خطا برمی‌گردانند.

پاسخ `200` از نوع `JourneyRecommendations` است:
`{state: ShoppingState, result: AlternativesResponse}`. وضعیت شامل شناسه و revision
درخواست، معیارها، مقایسه، `status=recommendations_ready` و `search_performed=true` است.
`result` پاسخ کامل Recommendation را با `original`، `suggestions`،
`original_constraints` و `original_verification` حفظ می‌کند. مدل دقیق در `openapi.json` است.
خالی‌بودن `result.original.recommendations` پاسخ موفق است؛ پیشنهادهای جایگزین، توضیحات
و پوشش داده نیز باید بررسی شوند. موجودی کالا همچنان تأییدنشده است.

`comparison` در صورت ارسال شامل `{request_id, revision, keys}` است؛ هر کلید از
`dataset_id`، `product_id` و `offer_id` تشکیل می‌شود و باید متعلق به درخواست و revision
جاری باشد. `status` و `search_performed` فقط خروجی‌اند و نباید در درخواست ارسال شوند.
برای پذیرش جایگزین، تغییرها باید صریحاً تأیید شوند؛ سپس معیارهای کامل به‌روز با revision
جدید و مقایسهٔ پاک‌شده ارسال شوند. endpoint مستقل پذیرش یا ثبت رضایت در سرور وجود ندارد.

| وضعیت | کدهای خطا |
| --- | --- |
| `422` | `invalid_request`، `missing_information`، `unsupported_constraint`، `invalid_recommendation_input` |
| `409` | `catalog_snapshot_changed` |
| `502` | `catalog_invalid_response`، `invalid_recommendation_data` |
| `503` | `catalog_unavailable` |
| `504` | `catalog_time_limit` |
| `500` | `internal_error` |

همهٔ خطاها ساختار `{error: {code, message, details}}` دارند. در خطای snapshot، نتایج و
مقایسهٔ قبلی کنار گذاشته و درخواست تازه ارسال شود؛ صفحات متعلق به snapshotهای متفاوت
نباید ترکیب شوند. جزئیات خطاهای سرویس، از جمله `retryable`، بدون تغییر حفظ می‌شوند.
CORS برای originهای تنظیم‌شده، روش‌های `GET` و `POST` و هدر `Content-Type` را می‌پذیرد.

## CatalogQuery

پارامترها query string هستند. فیلترهای ارسال‌شده با **AND** ترکیب می‌شوند.

| فیلد | معنا |
| --- | --- |
| `q` | متن اختیاری، حداکثر ۲۰۰ نویسه؛ جست‌وجوی پیشوند واژه‌ها در عنوان، برند، مدل و دستهٔ محصول |
| `category` | برابری نام دستهٔ محصول پس از یکسان‌سازی حروف؛ با دستهٔ فعالیت فروشگاه فرق دارد |
| `shop_id`، `product_id` | شناسهٔ واقعی دیتاست، بدون تولید شناسهٔ جایگزین |
| `min_price_toman`، `max_price_toman` | عدد صحیح مثبت به **تومان**؛ هر دو مرز شامل می‌شوند |
| `lat`، `lon` | نقطهٔ کاربر در WGS84؛ باید با هم ارسال شوند |
| `radius_km` | فاصلهٔ مستقیم تا فروشگاه، بیشتر از صفر و حداکثر ۱۰۰ کیلومتر؛ نیازمند مختصات |
| `sort` | `price_asc` پیش‌فرض، `price_desc`، `distance` یا `price_changed_desc` |
| `page` | از ۱ تا ۱۰۰۰۰ |
| `page_size` | از ۱ تا ۱۰۰، پیش‌فرض ۲۰ |

سقف پذیرفته‌شدهٔ قیمت در نسخهٔ اولیه `9_000_000_000_000` تومان است. مقادیر بزرگ‌تر
به‌عنوان دادهٔ نامتعارف از snapshot قابل جست‌وجو کنار گذاشته و در گزارش import ثبت می‌شوند؛
منبع اصلی دست‌نخورده می‌ماند. تغییر این سیاست نیازمند هماهنگی قرارداد با تیم است.

واژه‌های `q` همگی باید پیدا شوند. جست‌وجو مترادف، فهم متن آزاد یا رتبه‌بندی هوشمند ندارد؛
تبدیل نیاز کاربر به فیلتر بر عهدهٔ ماژول‌های journey/recommend است. `ی/ي`، `ک/ك`، ارقام،
اعراب و نیم‌فاصله یکسان‌سازی می‌شوند. قیمت‌ها برای نمایش به ریال تبدیل نشده‌اند.

`sort=distance` مختصات می‌خواهد. فروشگاه فاقد مختصات در جست‌وجوی معمولی می‌ماند و فاصله‌اش
`null` است؛ با فیلتر شعاع کنار گذاشته می‌شود و در مرتب‌سازی فاصله آخر قرار می‌گیرد.
فاصله به سه رقم اعشار نمایش داده می‌شود؛ فیلتر و مرتب‌سازی با مقدار کامل انجام می‌شوند.
این فاصله زمان سفر یا مسافت مسیر خیابان نیست.

ترتیب تساوی‌ها با `offer_id` ثابت می‌ماند. `total` تعداد **آفرها** است، نه محصولات یکتا.
هر پاسخ از یک snapshot دیتابیس خوانده می‌شود؛ اگر `context.dataset.dataset_id` بین صفحات
تغییر کرد، صفحه‌بندی را از ابتدا شروع کنید.

## شواهد و عدم قطعیت

- `OfferCandidate.evidence=offer_record`: ارتباط واقعی `offer → product + shop` وجود دارد.
- `ShopMatch.evidence=shop_record_only`: فقط رکورد فروشگاه/دستهٔ فعالیت تطبیق یافته است.
  از این پاسخ، فروش محصول خاص را نتیجه نگیرید.
- `availability=unconfirmed` و `requires_verification_before_visit=true` ثابت‌اند.
- `price_toman=null` یعنی قیمت ثبت نشده است؛ رابطهٔ آفر حفظ می‌شود. فیلتر بودجه این
  رکوردها را کنار می‌گذارد و در مرتب‌سازی قیمت، آخر قرار می‌گیرند. صفر قیمت معتبر نیست.
- `last_price_changed_at` زمان آخرین **تغییر قیمت**، با timezone و خروجی UTC است؛ ممکن است
  `null` باشد. این فیلد زمان بررسی موجودی، آخرین خزش یا قیمت زنده نیست.
- `context.dataset.source_kind` بین `sample` و `provided` فرق می‌گذارد. `provided` یعنی منبع
  ارائه‌شده، نه اینکه همهٔ نام‌ها یا شماره‌ها تأیید شده‌اند.
- نام فروشگاه‌ها ساختگی یا تأییدنشده و شماره‌های تماس ساختگی‌اند. `Shop` این وضعیت را
  صریح دارد. ساعت کاری و گزینه‌های پرداخت خام و ثبت‌شده‌اند؛ وضعیت `unsupported` را
  «باز است» تفسیر نکنید. تصاویر و لینک‌ها فقط داده‌اند و توسط بک‌اند واکشی نمی‌شوند.

مدل‌های مستقل recommendation باید شناسهٔ آفر و توضیح مستند را حفظ کنند و context را به UI
برسانند. داده‌های متنی دیتاست ورودی غیرقابل‌اعتماد هستند؛ آن‌ها را دستور agent تلقی نکنید.

## خطاها

خطاهای فیلتر `422`، شناسهٔ ناموجود `404` و خطای موقت دیتابیس `503` هستند:

```json
{"error":{"code":"invalid_query","message":"Check query parameters","details":[]}}
```

`details` برای اعتبارسنجی شامل محل و پیام فیلد است. پارامتر ناشناخته هم `422` می‌گیرد.
جست‌وجوی معتبرِ بدون نتیجه پاسخ `200` با `items=[]` دارد.

## تغییر قرارداد

فایل‌های JSON تولیدشده را دستی ویرایش نکنید. پس از تغییر مدل/route و بازبینی تیم:

```powershell
uv run python scripts/export_contracts.py
uv run python scripts/export_contracts.py --check
```

دستور دوم در CI هم اجرا می‌شود تا کد و فایل تحویلی از هم جدا نشوند. برای تغییر ناسازگار،
نسخهٔ قرارداد و مصرف‌کنندگان را با هم هماهنگ کنید.
